# Virtual financial agent

은행 앱의 계좌 조회·이체, 카드 분실 정지·재발급, 청구서 납부를 자연어 요청으로 처리하는 AI Agent입니다.
LangGraph로 업무 흐름(해석 → 검증 → 승인 → 실행 → 안내)을 구성하고, 데이터를 바꾸는 모든 업무는 처리안을 보여준 뒤 사용자 승인을 받아 실행합니다.

- LLM: Gemini (`gemini-3.6-flash`) — 요청 해석과 승인 응답 분류에만 사용
- 대상 확인·검증·데이터 변경: Python 함수
- 승인 대기·재개: LangGraph `interrupt` + SQLite 체크포인트
- 설계 자료: [docs/design_draft.md](docs/design_draft.md)

---

## 1. 실행 방법

### 준비

- Python 3.13 이상
- [uv](https://docs.astral.sh/uv/)
- Gemini API 키

```bash
uv sync
cp .env.example .env
```

`.env`에 `GEMINI_API_KEY`를 입력합니다. LangSmith 추적은 선택입니다.

### 실행

```bash
uv run python src/main.py
```

```
가상 금융 업무 에이전트입니다. ('도움말'로 사용법 확인, '종료'로 끝내기)

나> 내 계좌에 총 얼마 있어?
```

| 명령 | 동작 |
|---|---|
| `도움말` | 요청 예시와 명령 안내 |
| `초기화` | 업무 데이터와 대화 기록을 초기 상태로 되돌림 |
| `초기화 테스트` | 초기 데이터에 테스트 시드를 합쳐 초기화 (재발급 신청 제작 중·배송 중 상태 확인용) |
| `종료` | 프로그램 종료. 진행 중이던 업무는 다음 실행 때 이어서 확인 |

승인 질문에는 `승인`, `거절` 외에도 "응, 진행해", "취소할게", "아니, 5만 원만"처럼 자연어로 답할 수 있습니다.

### 실행 환경 참고

- **현재 사용자**: `user-001`로 고정되어 있습니다. 다른 사용자의 계좌·카드는 조회·변경 대상에서 제외됩니다.
- **기준일**: 실제 오늘 날짜(Asia/Seoul)를 사용합니다. 초기 거래가 2026년 8~9월에 있으므로 실행 시점에 따라 "이번 달" 조회 결과가 비어 있을 수 있습니다.
- **데이터 파일**

  | 파일 | 역할 |
  |---|---|
  | `data/initial_data.json` | 초기 데이터 원본 (수정하지 않음) |
  | `data/bank_data.json` | 작업용 복사본. 첫 실행 시 원본에서 자동 생성 (git 제외) |
  | `data/test_seed.json` | `초기화 테스트`에서 원본 위에 합치는 테스트 데이터 |
  | `data/checkpoints.sqlite` | 대화 진행 상태. 재시작 복구에 사용 (git 제외) |

- **저장 실패 재현**: `FAIL_SAVE_AT` 환경변수로 n번째 저장을 실패시킬 수 있습니다. 쉼표로 여러 개 지정할 수 있습니다.

  ```bash
  FAIL_SAVE_AT=3 uv run python src/main.py
  ```

## 2. 구조

```text
VirtualFinancialAgent/
├── data/                  # 원본·작업용·테스트 시드 데이터
├── docs/design_draft.md   # 설계 자료와 변경 이력
└── src/
    ├── main.py            # 입력 반복, 승인 응답 연결, 명령 처리, 재시작 복구
    ├── graph.py           # State, LLM 출력 스키마, 공통 노드 9개와 분기
    ├── functions.py       # 업무 함수(조회·검증·처리안·실행)와 TASKS 레지스트리
    └── data_store.py      # JSON 복사·읽기·저장(임시 파일 + 교체), 초기화
tests/                     # pytest (6절)
```

모든 업무가 같은 노드를 공유하고, 업무별 차이는 `functions.TASKS`에 등록한 함수로 처리합니다.

```text
parse_request ─ 조회 ─→ lookup ───────────────────────────────────────→ respond
              └ 변경 ─→ resolve ─→ create_request ─→ confirm ─→ execute ─→ next_task ─→ respond
                          │ ↑                          │ ↑ │        │         │
                          ↓ │                          │ └─┘        │         └ 남은 단계(정지 후 재발급) → resolve
                        ask_user (추가 질문·선택)       │ 판단 불가   └ 금액 변동(조건부 이체) → confirm
                                                       ├ 수정 → resolve
                                                       └ 거절 → next_task
```

## 3. 구현한 기능

### 계좌·이체

| 기능 | 구현 내용 |
|---|---|
| 계좌 조회·잔액 합산 | 계좌 목록, 계좌별 잔액, 총액 |
| 거래 내역 조회 | 기간(이번 주는 월~일, 시작·종료일 포함, 미지정 시 전체)·금액·유형(입금·출금·카드 결제)·계좌 조건, 최근순. 카드 결제에는 카드 이름 표시 |
| 즉시이체 | 출금·입금 계좌와 금액 확인 → 승인 → 잔액 2건·거래 2건 저장 |
| 조건부 이체 | 이체액 = 잔액 − 남길 금액. 0 이하면 실행하지 않음. 실행 직전 금액이 바뀌면 새 금액으로 재승인 |
| 여러 계좌 이체 | 입금 계좌별 금액과 총액 표시. 전체를 한 번에 저장하고 일부만 반영하지 않음 |
| 계좌 별명 변경 | 앞뒤 공백 제거 1~20자, 내 다른 계좌와 중복 금지 |

### 카드

| 기능 | 구현 내용 |
|---|---|
| 카드 조회 | 이름·ID·종류(체크·신용)·상태 |
| 분실 정지 | 사용 가능·일시 잠금 → 분실 정지 |
| 일시 잠금 / 잠금 해제 | 사용 가능 ↔ 일시 잠금. 분실 정지 카드는 해제할 수 없고 재발급을 안내 |
| 재발급 신청 | 분실 정지 카드만. 취소되지 않은 기존 신청이 있으면 안내. 배송지는 집·회사 중 선택. 기존 카드의 분실 정지는 유지 |
| 재발급 조회 | 신청이 여러 건이면 목록에서 선택, 없으면 기록 없음 안내 |
| 재발급 수정·취소 | 접수 상태에서만 가능. 제작 중·배송 중은 사유 안내 |
| 정지 후 재발급 | 정지와 재발급을 각각 승인. 이미 정지된 카드면 정지 단계를 건너뜀. 재발급이 실패·취소돼도 정지는 유지 |

### 청구서·납부

| 기능 | 구현 내용 |
|---|---|
| 미납 청구서 조회 | 납기일순 목록과 합계. 기한이 지난 청구서는 '연체료 없음' 표시 |
| 청구서 납부 | 잔액·출금 거래·청구서 상태를 한 번에 저장. 이미 납부한 청구서는 다시 처리하지 않음 |
| 일괄 납부 | 납기일 빠른 순서로 건별 저장. 잔액 부족 건은 미납 유지하고 다음 건 진행. 저장 실패 시 해당 건 미반영, 남은 건 미처리로 중단. 결과를 완료·실패·미처리로 안내 |

### 공통 대화·처리

| 기능 | 구현 내용 |
|---|---|
| 승인·거절, 자연어 승인·취소 | 처리안을 보여주고 `interrupt`로 대기. 답변을 LLM이 승인·거절·수정·판단 불가로 분류 |
| 승인 전 수정 | 바뀐 값만 반영해 다시 검증하고 처리안 전체를 다시 보여줌. 수정이 검증에 실패하면 기존 처리안 유지 |
| 추가 질문 | 빠진 정보를 묻고, 후보가 여러 개면 번호 목록에서 선택. "그냥 됐어"로 중단 가능 |
| 불완전·실행 불가 요청 | 검증 실패 사유를 안내. 지원하지 않는 요청은 가능한 업무와 예시를 안내 |
| 변경 결과 저장·조회 | 모든 조회는 매번 JSON을 새로 읽어 저장된 현재 값으로 안내 |
| 후속 결과 조회 | "아까 이체 됐어?" → 대화 중 마지막 요청의 상태·내용·결과. "그 전에 한 이체는?" → 직전 요청 이전 |
| 대화 대상 확인 | "그 카드" → 최근 다룬 대상이 1개면 사용, 여러 개면 그중 선택, 없으면 전체에서 확인 |
| 재시작·장애 복구 | 시작 시 중단된 업무를 확인. 이전 승인만으로는 실행하지 않고 재검증 후 새로 승인받음 |

## 4. 확인해 볼 요청 예시

```text
# 계좌·이체
내 계좌 목록과 잔액을 보여줘
내 계좌에 총 얼마 있어?
이번 달 생활비 출금 내역 보여줘
5만 원 이상 결제한 내역 찾아줘
생활비에서 저축으로 10만 원 옮겨줘        → (승인 질문에) 아니, 5만 원만 → 응, 진행해
저축으로 10만 원 옮겨줘                   → (추가 질문에) 생활비에서
생활비에 40만 원 남기고 나머지를 저축해줘
생활비에서 저축으로 20만 원, 여행 자금으로 10만 원 보내줘
여행 자금 계좌 이름을 휴가비로 바꿔줘

# 카드
내 카드 목록과 상태를 보여줘
생활비 카드를 집에 둔 것 같아. 잠깐 잠가줘
생활비 카드 찾았어. 잠금 풀어줘
생활비 카드를 잃어버렸어. 정지하고 재발급해줘
카드 재발급 신청 상태 알려줘
재발급 카드 배송지를 회사로 바꿔줘
재발급 신청 취소해줘

# 청구서
아직 안 낸 청구서 보여줘
생활비 계좌에서 전기요금 납부해줘
생활비 계좌에서 미납 청구서 전부 납부해줘

# 대화 맥락
생활비 카드 상태 알려줘 → 그 카드 잠가줘
아까 이체 됐어? → 그 전에 한 이체는?

# 실행할 수 없는 요청
이체해줘
생활비에서 저축으로 -1만 원 옮겨줘
오늘 날씨 어때?
```

제작 중·배송 중인 재발급 신청은 `초기화 테스트` 후 확인할 수 있습니다.

```text
초기화 테스트
카드 재발급 신청 상태 알려줘          → 3건 중 선택
여행 카드 재발급 배송지 회사로 바꿔줘   → 제작 중이라 변경 불가
교통 카드 재발급 신청 취소해줘         → 배송 중이라 취소 불가
```

## 5. 동작 확인 결과

2026-09-28, macOS, `gemini-3.6-flash`로 확인한 결과입니다. 확인 방법은 세 가지입니다.

- **대화**: `main.py`에 요청을 입력해 확인
- **대화 + 상태 조작**: 승인 사이 잔액 변경, 실행 도중 종료처럼 직접 만들기 어려운 상황은 스크립트로 데이터·체크포인트를 바꾼 뒤 `main.py`를 다시 실행
- **함수 테스트**: 업무 함수를 직접 호출해 검증·실행 결과와 저장된 데이터를 확인. 표에 따로 표시

위 결과의 대부분은 `tests/`의 자동 테스트로도 다시 확인할 수 있습니다 (6절).

### 5-1. 기능 동작

| 요청 | 결과 |
|---|---|
| 내 계좌에 총 얼마 있어? | 계좌 3개와 총 잔액 4,101,800원 안내 |
| 생활비에서 저축으로 10만 원 옮겨줘 → 아니, 5만 원만 → 응, 진행해 | 5만 원으로 처리안 전체를 다시 보여준 뒤 이체. 생활비 1,381,800원 |
| 저축으로 10만 원 옮겨줘 → 생활비에서 → 취소할게 | 출금 계좌를 질문해 반영, 거절 후 요청 `cancelled` |
| 여행에서 저축으로 1만원 보내줘 → 응 그 계좌 맞아 (그래프 직접 실행) | '여행'이 정확히 일치하지 않아 "여행 자금" 후보로 확인 후 진행 |
| 이번 달 생활비 출금 내역 보여줘 | 2026-09-01~09-30 생활비 출금 9건, 최근순, 카드 결제에 카드 이름 표시 |
| 생활비에 40만 원 남기고 나머지를 저축해줘 | 1,031,800원 이체, 생활비 400,000원 |
| 저축에서 생활비로 20만 원, 여행 자금으로 10만 원 → 아니 여행 자금은 5만 원만 | 계좌별 금액 수정 후 총 250,000원 이체 |
| 여행 자금 계좌 이름을 휴가비로 바꿔줘 → 휴가비 입금 내역 보여줘 | 별명 변경 후 새 이름으로 조회 가능 |
| 생활비 카드를 집에 둔 것 같아. 잠깐 잠가줘 → 찾았어. 잠금 풀어줘 | 사용 가능 → 일시 잠금 → 사용 가능 |
| 생활비 카드를 잃어버렸어. 정지하고 재발급해줘 → 승인 → 회사로 → 진행 | 정지 결과를 먼저 안내한 뒤 배송지 질문. 재발급 신청 `rei-001`, 두 요청은 `parent_request_id`로 연결 |
| 카드 재발급 신청 상태 알려줘 → 배송지 집으로 변경 → 신청 취소 | 조회·변경·취소 모두 처리, 카드는 분실 정지 유지 |
| 생활비 계좌에서 전기요금 납부해줘 | 42,000원 납부, 청구서 `paid`, 출금 거래(가맹점: 전기요금) 기록 |
| 통신비 내줘 → 생활비에서 | 계좌별 잔액을 보여주며 출금 계좌 질문 후 납부 |
| 생활비 카드 상태 알려줘 → 그 카드 잠가줘 → 아까 잠근 거 됐어? | 생활비 카드로 바로 처리, 요청 `완료` 상태와 결과 안내 |
| 내 카드 목록 보여줘 → 그 카드 잠금 풀어줘 | 최근 다룬 카드 2장 중에서 선택받음 |
| 이체 2번(완료·거절) → 아까 이체 됐어? → 그 전에 한 이체는? | 마지막 이체 '취소', 그 전 이체 '완료' 안내 |

### 5-2. 직접 선정한 실패 상황

| # | 상황 | 재현 방법 | 확인 결과 |
|---|---|---|---|
| 1 | 금액이 음수 | "생활비에서 저축으로 -1만 원 옮겨줘" | "이체 금액은 1원 이상의 정수여야 해요." 요청 기록 없음 |

### 5-3. 구현 중 발견한 LLM 동작

슬롯 필드가 늘어난 뒤 LLM이 가끔 업무 종류만 맞히고 슬롯은 모두 비워서 응답했습니다. 예를 들어 "이번 달 생활비 출금 내역"이 전체 기간 조회로 처리됐습니다. 출력 스키마에서 판단 필드(`intent`)가 슬롯 뒤에 있을 때 같은 요청 30회 중 5회 발생했고, 판단 필드를 앞으로 옮긴 뒤에는 0회였습니다. 원인과 수치는 [src/graph.py](src/graph.py)의 스키마 주석과 설계 변경 이력(v0.8)에 기록했습니다.

## 6. 테스트

```bash
uv run pytest
```

테스트마다 임시 폴더에 데이터를 복사해 사용하므로 `data/`의 작업 파일과 대화 기록은 바뀌지 않습니다.
그래프 흐름 테스트는 미리 정한 해석 결과를 돌려주는 가짜 LLM을 사용해 API 호출 없이 매번 같은 결과로 확인합니다.

| 파일 | 확인 내용 |
|---|---|
| `test_data_store.py` | 복사·저장·초기화, 저장 실패 시 기존 파일 유지, 테스트 시드 병합 |
| `test_accounts_transfer.py` | 계좌 조회, 즉시이체 검증 순서, 실행·중복 방지·재검증·저장 실패 |
| `test_cards.py` | 카드 조회·대상 확인, 상태 전이와 거부 사유, 잔액·거래 불변 |
| `test_reissue.py` | 재발급 신청·조회·변경·취소, 제작 중·배송 중 제한 |
| `test_bills.py` | 미납 조회, 한 건 납부, 일괄 납부(잔액 부족·저장 실패·재승인 후 이어서 처리) |
| `test_transactions_transfers.py` | 기간 계산, 거래 조회 필터, 조건부·여러 계좌 이체, 별명 변경 |
| `test_followup.py` | 후속 결과 조회, 대화 대상 추출, 대기 요청 정리 |
| `test_graph_flow.py` | 가짜 LLM으로 그래프 분기 확인: 수정·거절·추가 질문·복합 업무·재승인·지시어 |
| `test_recovery.py` | `main.App`을 다시 열어 재시작 복구 확인 |

실제 Gemini 테스트는 API 키가 필요하며 다음처럼 실행합니다.

```bash
RUN_LLM_TESTS=1 uv run pytest -m llm
```

2026-09-28 기준 결과: 기본 125개 통과(LLM 테스트 13개 건너뜀), LLM 테스트 13개 통과.

## 7. 제한 사항

- 사용자는 `user-001` 한 명으로 고정되어 있고 로그인·인증은 없습니다.
- 재발급 카드의 제작·배송 진행은 구현하지 않았습니다. 제작 중·배송 중 상태는 테스트 시드로만 준비합니다.
- 요청 해석은 LLM 결과에 의존하므로 같은 문장도 드물게 다르게 해석될 수 있습니다. 대상과 금액은 항상 처리안에 표시되어 승인 전에 확인할 수 있고, 검증은 Python이 수행합니다.
- 결과 안내 문장은 LLM이 아닌 템플릿으로 만듭니다. 금액·잔액을 정확하게 안내하는 대신 표현이 다양하지 않습니다.
