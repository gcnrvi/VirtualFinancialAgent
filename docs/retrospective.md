# 회고

## 1. 프로젝트 요약

은행 앱의 계좌·이체, 카드 분실 정지·재발급, 청구서 납부 업무 20개를 자연어로 처리하는 에이전트를 LangGraph로 만들었다.
설계 초안(v0.3) → 1~6단계 구현 → 최종 설계 순서로 진행했고, 단계마다 설계를 고치고 커밋했다(설계 v0.1~v0.9, 커밋 15개).
최종 결과는 공통 노드 9개와 업무 레지스트리로 이루어진 그래프, pytest 125개(가짜 LLM)와 실제 LLM 테스트 13개다.

## 2. 배운 점

### LLM에게 맡길 일과 맡기지 않을 일을 나누는 것이 설계의 중심이었다

처음부터 "LLM은 문장을 해석만 하고, 대상 확인·검증·데이터 변경은 Python이 한다"는 원칙을 정했다. 구현하면서 이 원칙이 여러 번 판단 기준이 됐다.

- 날짜 계산: LLM은 "이번 주"를 `this_week`로 분류만 하고, 월~일 범위는 Python이 계산한다.
- 지시어: "그 카드"의 이름을 LLM이 추측하지 않게 하고, 어느 항목을 가리키는지만 표시하게 했다(`referenced_slot`).
- 결과 안내: 금액을 틀리게 말할 위험 때문에 LLM 대신 템플릿 문장으로 만들었다.

LLM이 틀리게 해석해도 처리안이 승인 전에 표시되고 검증은 Python이 하기 때문에, 잘못된 변경이 바로 실행되지 않는다.

### `interrupt`는 어디에 두느냐가 중요하다

재개하면 노드가 처음부터 다시 실행되기 때문에, 부작용이 있는 코드 뒤에 `interrupt`를 두면 같은 작업이 두 번 실행될 수 있다. 그래서 승인은 전용 노드(`confirm`)에서만 받고, 실행(`execute`)은 승인 뒤 별도 노드로 분리했다.

### 업무별 노드보다 공통 노드 + 레지스트리가 확장에 유리했다

업무가 20개라 업무마다 노드를 만들면 승인·수정·거절 흐름이 20번 반복된다. 초안에서 공통 노드 9개와 `TASKS` 레지스트리로 정했고, 2~6단계에서는 대부분 `functions.py`에 함수를 추가하고 등록하는 것만으로 기능을 늘릴 수 있었다. 반대로 공통 흐름 자체를 바꿔야 할 때(조회에서 추가 질문, 복합 업무, 금액 변동 재승인)는 모든 업무에 영향이 가서 테스트가 꼭 필요했다.

### 저장소가 둘이면 "무엇을 기준으로 할지"를 먼저 정해야 한다

대화 진행 상태는 SQLite 체크포인트, 업무 데이터는 JSON에 있어서 둘이 어긋나는 경우가 생긴다(예: 이체는 JSON에 저장됐는데 체크포인트는 실행 전에서 멈춤). "JSON의 요청 상태를 기준으로 한다"와 "승인 대기 상태일 때만 실행한다"는 두 규칙을 정한 덕분에 중복 이체 없이 복구할 수 있었다.

### LLM 출력 스키마는 필드 순서도 결과에 영향을 준다

슬롯이 늘어난 뒤, 업무 종류는 맞히면서 슬롯은 모두 비워서 응답하는 경우가 생겼다. 같은 요청을 30회씩 보내 비교해 보니 `intent`가 슬롯 뒤에 있을 때 5회, 앞에 있을 때 0회였다. 추측으로 프롬프트를 고치기 전에 반복 측정으로 원인을 확인한 것이 도움이 됐다.

### LLM이 들어간 흐름도 결정적으로 테스트할 수 있다

처음에는 실제 LLM으로 대화를 돌려 확인했는데, 느리고 결과가 매번 조금씩 달랐다. 미리 정한 해석을 돌려주는 가짜 LLM을 넣자 그래프 분기와 재시작 복구를 1초 안에 매번 같은 결과로 확인할 수 있었다. 실제 LLM 테스트는 요청 해석만 따로 확인하도록 분리했다.

## 3. 어려웠던 점과 해결 과정

| 문제 | 원인 | 해결 |
|---|---|---|
| 추가 질문에 답하면 앞서 말한 값이 사라짐 | 초안대로 `ask_user → parse_request`로 돌아가면 답변이 새 요청으로 해석되어 업무 필드가 초기화됨 | 답변은 `SlotAnswer`로 해석해 기존 값에 병합하고 `resolve`로 돌아가게 변경 |
| "1억으로 바꿔줘" 한 마디에 요청 전체가 실패 | 수정한 값이 검증에 실패하면 실패로 종료 | 수정 직전 값을 `slots_backup`에 두고, 실패하면 되돌려 기존 처리안으로 다시 질문 |
| 정지 후 재발급에서 정지 결과를 모른 채 배송지 질문을 받음 | 단계별 결과를 마지막에 한꺼번에 안내 | 결과를 `log`에 쌓고, 아직 안 보여준 결과를 다음 질문 앞에 먼저 표시(`log_shown`) |
| 이미 정지된 카드로 "정지하고 재발급해줘" 하면 전체 실패 | 1단계 검증 실패로 복합 업무가 중단 | 이미 원하는 상태면(`already`) 그 단계를 건너뛰고 다음 단계 진행 |
| 일괄 납부 도중 종료 시 어디까지 냈는지 알 수 없음 | 명세상 건별 저장인데 요청 기록은 마지막에만 저장 | 건별 저장에 진행 기록(`result.items`)을 함께 저장. 재시작하면 재검증에서 낸 건이 빠져 남은 건만 재승인 |
| 그래프는 끝났는데 요청만 승인 대기로 남음 | 일괄 납부의 최종 기록 저장이 실패하는 경우. 복구 로직이 체크포인트만 확인 | 시작할 때 대화와 연결되지 않은 대기 요청을 찾아 안내하고 정리(`close_orphan_requests`) |
| "그 전에 한 이체는?"에 직전 이체를 또 답함 | "그 전"을 표현할 슬롯이 없음 | `earlier_request`를 추가해 마지막 요청과 그 이후를 제외 |
| 테스트가 실제 데이터와 대화 기록을 바꿈 | 테스트 스크립트가 `data/`를 직접 사용. `graph.py`가 체크포인트 경로를 import할 때 고정 | 테스트마다 임시 폴더로 격리하고, 체크포인트 경로를 실행 시점에 읽도록 변경 |
| "생활비으로", "카드을(를)" 같은 어색한 조사 | 템플릿 문장에 이름을 그대로 넣음 | 받침에 맞춰 조사를 붙이는 함수(`with_ro`, `with_eul`, `with_eun`) 추가 |

## 4. 남은 한계와 개선하고 싶은 점

| 한계 | 개선 방향 |
|---|---|
| 사용자가 `user-001` 하나로 고정되어 있고 인증이 없다 | 로그인한 사용자 ID를 세션에서 받아 `thread_id`와 데이터 필터에 사용 |
| LLM은 현재 문장만 본다. 대화 맥락은 `last_targets`로만 전달해서 "그거 말고 저축으로" 같은 표현은 처리하기 어렵다 | 최근 몇 턴의 대화를 요약해 해석 프롬프트에 함께 전달 |
| 대화 기록(`messages`)이 체크포인트에 계속 쌓인다 | 오래된 메시지를 잘라내거나 요약(`trim_messages`) |
| LLM 호출 실패 시 재시도 없이 "해석하지 못했어요"로 끝난다 | 짧은 재시도와 대체 모델 |
| JSON 파일 저장은 여러 프로그램이 동시에 실행되는 상황을 고려하지 않았다 | SQLite 같은 DB로 옮겨 트랜잭션으로 원자성 보장 |
| `functions.py`가 2,000줄이 넘는다 | 계좌·카드·재발급·청구서·공통으로 모듈 분리 |
| 여러 계좌 이체에서 입금 계좌 이름이 모호하면 선택받지 않고 실패로 안내 | 목록 항목별 후보 선택 지원 |
| 거래 내역이 많아지면 한 번에 모두 출력 | 건수 제한과 "더 보기" |
| 기준일이 실제 오늘이라 시간이 지나면 "이번 달" 조회 결과가 비어 보인다 | 실행 옵션으로 기준일 지정 |
| 실제 LLM 해석 테스트가 13건뿐이고 결과가 비결정적이다 | 요청 예시를 늘린 평가셋을 만들어 정확도를 수치로 관리 |
| 재발급 카드의 제작·배송 진행은 테스트 데이터로만 존재 | 상태를 진행시키는 관리자 기능 또는 시간 경과 시뮬레이션 |

## 5. 진행 방식 돌아보기

- 설계 초안(v0.3)을 먼저 확정하고 1~6단계로 나눠 구현했다. 단계마다 동작을 확인한 뒤 커밋했고, 설계와 달라진 점은 바로 변경 이력에 이유와 함께 남겼다.
- 수동 확인에서 테스트로: 처음에는 대화를 직접 돌려 확인했지만, 기능이 늘어날수록 이전 단계가 깨지지 않았는지 확인하는 데 시간이 들었다. 단계마다 회귀 테스트를 돌린 것이 공통 흐름을 바꿀 때 특히 도움이 됐다.
- README를 쓰면서 확인 결과의 출처(대화 / 상태 조작 / 함수 테스트)를 다시 대조했고, 일부는 대화가 아니라 함수 테스트로 확인한 것이어서 표시를 고쳤다. 테스트를 옮기면서는 기록한 출력이 이후 변경 전의 결과였던 경우도 발견했다. 결과를 적을 때는 언제, 어떻게 확인했는지까지 남겨야 한다는 것을 배웠다.
